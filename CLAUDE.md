# Notes for agents working on this project

- `profile/master_profile.md` is the only source of facts about the user. It and `resume/resume.md` are not in git (`.gitignore`); git has made-up `*.example.md` copies. The user's name and contact details are `MY_*` in `.env` (`config.my_details`, and `my_details` in `build.py`), each winning over the same Basics line; never write real contact details, salary or the like into a tracked file (tests use made-up ones). Generated CVs, cover letters and application answers may reorder, emphasize, rephrase and remove, and must NEVER add a skill, technology, employer, title, date, responsibility, achievement or metric that is not in that file. `TODO` entries are unknown: leave them out. Code reads the file in `profile.py` (`load_profile`, `sections`, `split_tags`, `strip_notes`); the checks on generated lines (numbers, names, skills, seniority words, years) share their building blocks in `grounding.py`, used by `check_draft` (pitch), `check_bullet` (cv) and `check_sentence` (cover), so a change there changes all three.
- Deterministic code decides filtering, dedup and eligibility, and every verdict carries a quotable reason. LLM judgment on eligibility belongs only on jobs with status `needs_review` (eligibility `unclear`). Do not replace a rule that quotes evidence with a guess. (Contacts and email drafts are separate LLM uses, each checked by code; see below.)
- Fit grade (`fitgrade.py`, `config/fit_grade.json`, `jobhunter grade`): DeepSeek grades each shown job 1-5 with one sentence, for SORTING ONLY (report, To apply, which jobs get a CV first). It never changes `status`, never hides or rejects a job, and is stored in `jobs.fit_grade_json` so `reclassify` keeps it. It learns only from examples, never from rules you write for it: the profile's facts (via `profile.load_profile`, so no contact details), the user's `preferences` text, and their Applied jobs and skipped jobs with `applications.skip_reason`/`skip_note` (one-tap reasons, `tracking.SKIP_REASONS`). The user set Reached out / Interviewing by hand for other reasons: never use stages as like/dislike signals. Stated 5+ years is ranked down by the grade, not rejected (user's choice, 2026-10-19), except for the junior-only roles below.
- Years of experience (`extract.find_required_yoe`): read per sentence (a "nice to have" cancels only its own sentence), and the reason quotes the sentence. Check a new pattern against the stored jobs (old vs new `required_yoe`) before shipping: company history ("for the past 12+ years") and benefits ("after 5+ years") are not requirements.
- Junior-only roles (`junior_only` in `config/filters.json`, `relevance.junior_only_role`): AI engineer, AI automation and forward-deployed titles (a word from `roles`, or `_AI_ROLE`) are wanted only at junior level (the user's call 2026-10-20): rejected, code `junior_only`, when the title says "senior"/"lead" or the posting asks for 3+ years, quoted. A title that also says backend or full stack keeps the usual rules, as do backend, software and solutions roles (6+ rejected). The years can be in any field ("3+ years of software, 1+ with LLMs" counts as 3); no years stated is kept.
- Outreach (`jobhunter serve`, `src/jobhunter/web/`): `contacts.py` (Hunter first, Claude web search as backup; who to target by size is plain code; a web-found name is "confirmed" only when `find_quote` finds it in text the API returned), `pitch.py` (fixed text by default; with `pitch_mode` "ai" the model writes only the one-sentence proof line, through `llm.json_model`; `check_draft`, built on `grounding.py`, blocks any number, skill or title not in the profile facts it cites), `mailer.py` (Gmail app password: SMTP send, IMAP read-only scan), `tracking.py` (stages, follow-ups, ghosting). Emails are sent ONLY from the Send button (`POST /api/jobs/{id}/send`); never add automatic sending, including follow-ups. The tables `companies`, `contacts`, `applications`, `events`, `sent_mail`, `mail_seen` are separate from `jobs`, so `reclassify` never touches them. Pipeline order (the user's call 2026-10-23): To apply by posting day, newest first; the Email someone column (`tracking.needs_email`: Reached out, nobody at the company emailed, no reply, within `reach_out_days` (7) of `reached_out_at`) and Reached out by `reached_out_at` (later of applied/emailed, else when you moved it), newest first. It is a list to act on by hand, never a send.
- Web app security: 127.0.0.1 only, Host check, and every change request needs the startup token (`X-JH-Token`) and a JSON body. Keep it that way; no CORS, except GET `/api/cv/...` (`Access-Control-Allow-Origin: *` and `Allow-Private-Network`), so the Chrome extension can attach a CV on a job site; it only reads PDFs listed in `cv_dir`.
- Tailored CVs (`cv.py`, `jobhunter tailor`, the Tailor CV button): the model only orders and rewords profile bullets and picks skills; code copies names, employers, dates and education from `resume.md` in `resume_dir` and checks each bullet against the profile bullets it cites (`check_bullet`), each skill against the profile row. A rewrite never shortens a bullet: it may drop at most `MAX_DROPPED_WORDS` (1) of the cited bullet's words, and code puts back the profile's bold (`restore_bold`: `**800+**`), which the model's text does not carry (the user's call 2026-10-23: the model had cut clauses and an "estimated"). The headline is the posting's own title, cleaned by code (`cv_headline`: "Senior Software Engineer, Payments Platform" -> "Senior Software Engineer", "Senior Backend & Platform Engineer" -> "Senior Backend Engineer", levels like II and words like Remote/Junior/Freelance dropped; the user's call 2026-10-23); a title that does not read as one engineering role gets the model's pick from the target roles, with a note. A failed rewrite prints the profile's own words. The model never writes a Summary: the `## Summary` paragraph in resume.md is the user's own (also in the profile, stated 2026-10-20) and is copied word for word like the other non-role lines. `build.py` in `resume_dir` makes the PDF; never overwrite a version the app did not write. Your hand edits (`cv.save_version`, the Edit CV text box, `jobhunter rebuild-cv`) are the exception: they rewrite the job's `versions/<name>.md` (keeping `.md.bak`) and only rebuild the PDF, with no model; `check_version` lists lines that say more than the profile but never changes them. A tailored CV with `edited_at` is not re-tailored unless `replace_edits`.
- The profile is the bullet library: every Experience bullet starts with tags (`[core]` always prints; `[lead]`/`[fullstack]`/`[automation]`/`[mobile]` only when `cv.job_tags` matches the job, by phrases in `TAG_RULES` or `cv_tags` in outreach.json, each with a quotable reason). Which bullets print is code's decision, never the model's; a bullet the model leaves out is appended in the profile's words. `Printed title:` lines choose the role's title the same way; the `###` heading keeps the real title, which `_match` also accepts. Notes on a bullet must be `(Confirmed by me ...)` or they print; any other `- ` line under a role becomes a bullet. Tests use a frozen copy, `tests/fixtures/profile/master_profile.md`, because they cite bullets by position; `test_your_profile_is_well_formed` checks only the shape (known tags, no leaking notes) of the real profile, when there is one, and of the example, so editing the real profile never needs test changes. A CV still 2 pages in compact mode drops optional bullets (`cut_optional`, oldest role first), never core ones. `build.py sync` (in `resume_dir`) copies the tagged bullets into resume.md; `build.py new <Role> <Company> [tag ...]` applies the same tags by hand.
- Cover letters (`cover.py`, `jobhunter cover`, the Write cover letter button): only when the user asks; the daily run writes none (`auto_cover` false, the user's call 2026-10-20). Only two paragraphs, no header, date, greeting or sign-off (the user's call 2026-10-20); the page's Download button saves the text as `.txt` in the browser: (1) why this company, written by `cover_model` (`claude-code`, the user's pick over DeepSeek on 2026-10-20: DeepSeek read as AI) from the posting and up to 3 pages code fetches from the company's site (`research`: home, /about, /blog; domain from `companies.domain`, the job's links, else a `<name>.com` guess kept only when the page names the company; none for job boards/agencies), and (2) `cover_paragraph` from outreach.json, the user's own words, printed as is and never checked. `check_sentence` makes every name, number and company-kind word (`_COMPANY_KIND`: "consultancy", "startup") be in the posting, the pages or the profile facts (`load_letter_facts`, the CV's tags, never logistics lines); a sentence with I/my names only profile tools and years. Paragraph 1 is about the company, never a pitch: the writer never sees the profile facts (they are only for the checks), and a sentence that describes the user's past work (`_PAST_WORK`: "I built/led", "my experience", "similar") or names an employer is dropped; a number is sent back once (their headline stats read as a website summary). The model names its one reason, then quotes the words it rests on (`find_quote`); a third try only when too little would be left. A sentence that fails after one retry is dropped and listed in `removed`; length (2-3 sentences, 65 words), dashes and an unfound quote are sent back once, then noted. How paragraph 1 reads lives in `config/cover_letter_guidelines.md` (the `writer:start`/`writer:end` part follows `SYSTEM`; `check_style` reads its "Never use" and "Use at most one" lists); the facts rules stay in code. Stored in `applications.cover_letter_json`; the file is `cv_dir/<Last>_CoverLetter_<Company>_<MonYYYY>.md`; never overwrite a letter the app did not write.
- The resume folder is `resume/` in the project (`build.py`, `resume.example.md` tracked; `resume.md`, `versions/`, `output/`, `applications.csv` ignored). PDFs and letters start with the last word of the name (`<Last>_Resume_General.pdf`); empty `default_cv` means that file. Relative `resume_dir`/`cv_dir` resolve against the project root (`OutreachConfig.load`). The daily run's CV step (and letter step, when `auto_cover` is on) also catch up on shortlisted jobs from the last `catch_up_days` that have none (`outreach.to_prepare`).
- Shared Claude helpers (`find_quote`, `pages_read`, `Usage`, `forced_tool_choice`, `JsonModel` for one JSON answer from Claude, DeepSeek or the Claude Code CLI) live in `llm.py`. `json_model` builds one from a model name (and says which key is missing): pitch, cv, cover, fitgrade, posted_date and ai_check's DeepSeek/Claude Code steps all use it; only `contacts.py` and ai_check's `AiChecker` (claude-* models) call `messages.create` themselves, for the API's server-side web search. Opus 5.5 rejects a forced `tool_choice`, so use `forced_tool_choice(model, name)`.
- The eligibility LLM step is `ai_check.py`: DeepSeek over pages code fetched (`PagesChecker`; ATS postings through their public APIs), then the Claude Code CLI with WebSearch/WebFetch for jobs it could not settle (`WebChecker`, `web_model`); `claude-*` models use the API's own web search. It changes a status only when its quote is found word for word in the description or a page the API or code fetched (`find_quote`); never trust a quote only the model saw; `classify.apply_ai_check` combines it with the rules, and results live in `jobs.ai_check_json` so `reclassify` keeps them. Its verdict `sponsors_visa` (the company sponsors a work visa for the role, in any country: the user's call 2026-10-22) shortlists the job as `likely` (`ai_sponsors_visa`) only when the quote is found and `visa.read_posting` also reads it as an offer with no refusal. The 401(k) rule still applies to these.
- Location conflicts (`eligibility._assess_remote`): a location that fits, narrowed somewhere else ("Worldwide", but "must be based in the UK"; "EMEA", but location "Remote, United Kingdom"), is rejected, code `location_conflict`, quoting both (the user's call 2026-10-22); narrowed to the UAE/Qatar the relocation rules judge it, to a visa-list country the visa rules. A restriction the posting doubts ("Remote - Europe (UTC-1 to UTC+3)", "US only" next to "we hire globally") stays `unclear`. A salary-range sentence ("applies to US-based candidates only") is not a location rule.
- Posting dates (`posted_date.py`, `jobhunter dates`, `find_dates` in `config/ai_check.json`): an undated job is never shortlisted, so before the AI check the daily run looks up undated needs_review jobs: code reads the schema.org `datePosted` on the job's own pages, else `web_model` (Claude Code with web search) quotes the words that state the date; code finds the quote on the page it fetched and reads the date from the quote (`date_in`), never the model's own date. The date goes into `posted_at`, the evidence into `jobs.date_check_json`, and the usual age rule judges the job.
- A source's "no location given" is unknown, never "Worldwide" (Himalayas shows "Worldwide" for US-only roles).
- The SQLite DB (`data/jobs.sqlite`) is the memory; Markdown reports are output only. Rejected jobs stay stored on purpose, so they never reappear as new.
- Reports are `reports/<YYYY-MM-DD>.md`, one per day, rendered from `jobs.report_date` (see `store.py`); there is no `latest.md` or run-numbered file. A date-range run (`--from/--to`) fetches once and files jobs by posting day.
- Watched boards (`boards.py`): after each run, the Greenhouse/Lever/Ashby board of each company with a shortlisted job is added to the `watched_boards` table (from the job's own link, or a guessed slug kept only when the board lists the job's title or names the company, with that evidence as `reason`) and fetched from the next run on. Never job sites, agencies or blocked companies; a removed board stays removed. Settings: `watch_boards` in `config/sources.json` (not a source; `sources.SETTINGS`).
- Agencies (`agency.py`, `agencies` in `config/filters.json`): rejected right after `blocked_companies`, code `agency`, quoting the name, the name word or the sentence. Only add a phrase after checking it against the stored jobs: "our clients", "talent pool", "talent network" are in real companies' postings.
- Relocation (`relocation.py`, `relocation` in `config/filters.json`): in the UAE or Qatar an on-site/hybrid job (or "Remote (UAE)") is judged by `assess_relocation`, never `unclear` (so the AI check, which asks about remote hiring from Lebanon, skips it). The pay floor is `RELOCATION_MIN_MONTHLY_USD` in `.env`, never in a tracked file. AED/QAR/SAR pay with no period is monthly (`extract._MONTHLY_BY_DEFAULT`).
- Visa list (`visa.py`, `sponsors.py`, `visa_list` in `config/filters.json`): a target role in the Netherlands, Germany, Finland, the UK, Ireland, Spain or Italy (on-site/hybrid, or remote only for people living there, i.e. one the remote rules reject) gets status `visa_list`, a separate list (report section, web view `visa_list`), never `shortlisted`, so it stays out of the report's Shortlisted section and the daily CV/letter/contact steps. The pipeline's To apply column does show the ones posted today or yesterday (stage new, the date the row shows: `view=visa_list&days=2`, with a `visa` chip), next to the shortlisted jobs. Only with quoted evidence: the posting offers a visa (`visa_offered`, also an HN "VISA" header), offers relocation help without naming a visa (`relocation_offered`, weaker), or the company is on its country's government list (`visa_register`: UK Skilled Worker register, Dutch IND recognised sponsors, Irish employment-permit companies; on-site/hybrid only). Rejected: `no_sponsor` (refuses, or wants a right to work, including a British nationality: "Sole British National", "must be a UK national"; never "UK national security clearance"), `language_required` (asks for or is written in a language not in the profile), `no_visa_evidence`. Each clause is judged alone ("Visa sponsorship available (no relocation support)" is an offer); "sponsorship" alone never counts. A remote job open to Lebanon is never moved to the visa list. The lists live in `data/sponsors/` (`jobhunter sponsors --update`; the daily run refreshes them every `refresh_days`); a one-word UK name needs the register's town in the job's location. The Gulf `relocation` rules are separate and unchanged.
- A posting that mentions a 401(k) is rejected (`classify.us_benefits`, code `us_benefits`, the line quoted), whatever its location or AI check says, unless it is on the visa list (it sponsors the move; big companies list every country's benefits): the user's call (2026-10-19), knowing it also drops global-remote companies like Metabase that offer one to US staff. Do not soften it into a doubt or a grade signal.
- One job per company (`report.one_per_company`, `onePerCompany` in `app.js`): the report sections, the To apply column and Today's new-job lists show each company's best job (grade, then fit) and name or fold the rest ("Also at Palantir (16 more)", "+16 more at Palantir"): one board fetch brought 17 Palantir London roles on 2026-10-21 (the user's call). Display only: never a status, a reject code or the CV step.
- `blocked_companies` in `config/filters.json` rejects a company before any other rule (code `blocked_company`, its `why` quoted): companies the user never wants shortlisted again.
- After changing `config/filters.json` or the rules, run `.venv/bin/jobhunter reclassify`.
- Tests: `.venv/bin/pytest`. A new source = a module in `src/jobhunter/sources/` with `from_config()`, an entry in `BUILDERS`, and a test against a trimmed real response in `tests/fixtures/`. `tests/fixtures/hunter_*.json` are Hunter's documented examples (no key yet): replace them with trimmed real responses once `HUNTER_API_KEY` is set. Tests never reach Hunter, Claude or Gmail (`conftest.no_real_keys`).
- LinkedIn (`sources/linkedin.py`) is read through its logged-out job search, the user's choice (2026-10-21) knowing its terms forbid it: keep it slow (`pause`, about 1 request/s gets 429), by place (UAE, Qatar, Lebanon, UK/NL "visa sponsorship"; logged out the remote and level filters do nothing), and never fetched twice in a run (`refetch = False`, like SerpApi). Remote Rocketship's terms forbid scraping: do not build it.
- Each run waits for the network first (`http.wait_for_network`: the scheduled runs start as the Mac wakes) and fetches a source with a ConnectError once more (`pipeline.fetch_all`).
- Error lines go through `sources.base.describe_error`, which drops query strings, so the SerpApi key never reaches logs or reports. The `httpx` logger stays at WARNING for the same reason.
