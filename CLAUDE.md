# Notes for agents working on this project

- `profile/master_profile.md` is the only source of facts about the user. Generated CVs, cover letters and application answers may reorder, emphasize, rephrase and remove, and must NEVER add a skill, technology, employer, title, date, responsibility, achievement or metric that is not in that file. `TODO` entries are unknown: leave them out.
- Deterministic code decides filtering, dedup and eligibility, and every verdict carries a quotable reason. LLM judgment on eligibility belongs only on jobs with status `needs_review` (eligibility `unclear`). Do not replace a rule that quotes evidence with a guess. (Contacts and email drafts are separate LLM uses, each checked by code; see below.)
- Outreach (`jobhunter serve`, `src/jobhunter/web/`): `contacts.py` (Hunter first, Claude web search as backup; who to target by size is plain code; a web-found name is "confirmed" only when `find_quote` finds it in text the API returned), `pitch.py` (Claude writes only the hook and 1-2 sentence pitch; `check_draft` blocks any number, skill or title not in the profile facts it cites), `mailer.py` (Gmail app password: SMTP send, IMAP read-only scan), `tracking.py` (stages, follow-ups, ghosting). Emails are sent ONLY from the Send button (`POST /api/jobs/{id}/send`); never add automatic sending, including follow-ups. The tables `companies`, `contacts`, `applications`, `events`, `sent_mail`, `mail_seen` are separate from `jobs`, so `reclassify` never touches them.
- Web app security: 127.0.0.1 only, Host check, and every change request needs the startup token (`X-JH-Token`) and a JSON body. Keep it that way; no CORS.
- Tailored CVs (`cv.py`, `jobhunter tailor`, the Tailor CV button): the model only orders and rewords profile bullets and picks skills; code copies names, employers, dates and education from `resume.md` in `resume_dir` and checks each bullet against the profile bullets it cites (`check_bullet`), each skill against the profile row, the headline against the target roles. A failed rewrite prints the profile's own words. Never add a Summary section. `build.py` in `resume_dir` makes the PDF; never overwrite a version the app did not write.
- The profile is the bullet library: every Experience bullet starts with tags (`[core]` always prints; `[lead]`/`[fullstack]`/`[automation]`/`[mobile]` only when `cv.job_tags` matches the job, by phrases in `TAG_RULES` or `cv_tags` in outreach.json, each with a quotable reason). Which bullets print is code's decision, never the model's; a bullet the model leaves out is appended in the profile's words. `Printed title:` lines choose the role's title the same way; the `###` heading keeps the real title, which `_match` also accepts. Notes on a bullet must be `(Confirmed by me ...)` or they print; any other `- ` line under a role becomes a bullet. Tests use a frozen copy, `tests/fixtures/profile/master_profile.md`, because they cite bullets by position; `test_your_profile_is_well_formed` checks only the real profile's shape (known tags, no leaking notes), so editing the real profile never needs test changes. A CV still 2 pages in compact mode drops optional bullets (`cut_optional`, oldest role first), never core ones. `build.py sync` (in `resume_dir`) copies the tagged bullets into resume.md; `build.py new <Role> <Company> [tag ...]` applies the same tags by hand.
- Cover letters (`cover.py`, `jobhunter cover`, the Write cover letter button): facts are only what the job's CV prints (`load_letter_facts`, same tags), never the salary line. The model writes opening, cited paragraphs, closing; `check_sentence` checks each sentence (paragraphs against the facts they cite; opening/closing may repeat posting numbers about the company, but a sentence with I/my names only profile tools). A sentence that fails after one retry is dropped and listed in `removed`, never printed. Gaps are never claimed: code writes `cover_gap_text`, and a gap must be in the posting and share no word with the facts (`valid_gap`). Stored in `applications.cover_letter_json`; the file is `cv_dir/<Last>_CoverLetter_<Company>_<MonYYYY>.md`; never overwrite a letter the app did not write.
- The resume folder is `resume/` in the project (`build.py`, `resume.md` tracked; `versions/`, `output/`, `applications.csv` ignored). Relative `resume_dir`/`cv_dir` resolve against the project root (`OutreachConfig.load`). The daily run's CV and letter steps also catch up on shortlisted jobs from the last `catch_up_days` that have none (`outreach.to_prepare`).
- Shared Claude helpers (`find_quote`, `pages_read`, `Usage`, `forced_tool_choice`, `JsonModel` for one JSON answer from Claude or DeepSeek) live in `llm.py`. Opus 5.5 rejects a forced `tool_choice`, so use `forced_tool_choice(model, name)`.
- The eligibility LLM step is `ai_check.py` (Claude + web search). It changes a status only when its quote is found word for word in the description or a page the API fetched (`find_quote`); `classify.apply_ai_check` combines it with the rules, and results live in `jobs.ai_check_json` so `reclassify` keeps them.
- A source's "no location given" is unknown, never "Worldwide" (Himalayas shows "Worldwide" for US-only roles).
- The SQLite DB (`data/jobs.sqlite`) is the memory; Markdown reports are output only. Rejected jobs stay stored on purpose, so they never reappear as new.
- Reports are `reports/<YYYY-MM-DD>.md`, one per day, rendered from `jobs.report_date` (see `store.py`); there is no `latest.md` or run-numbered file. A date-range run (`--from/--to`) fetches once and files jobs by posting day.
- After changing `config/filters.json` or the rules, run `.venv/bin/jobhunter reclassify`.
- Tests: `.venv/bin/pytest`. A new source = a module in `src/jobhunter/sources/` with `from_config()`, an entry in `BUILDERS`, and a test against a trimmed real response in `tests/fixtures/`. `tests/fixtures/hunter_*.json` are Hunter's documented examples (no key yet): replace them with trimmed real responses once `HUNTER_API_KEY` is set. Tests never reach Hunter, Claude or Gmail (`conftest.no_real_keys`).
- Error lines go through `sources.base.describe_error`, which drops query strings, so the SerpApi key never reaches logs or reports. The `httpx` logger stays at WARNING for the same reason.
