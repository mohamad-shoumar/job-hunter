# Notes for agents working on this project

- `profile/master_profile.md` is the only source of facts about the user. It and `resume/resume.md` are not in git (`.gitignore`); git has made-up `*.example.md` copies. The user's name and contact details are `MY_*` in `.env` (`config.my_details`, and `my_details` in `build.py`), each winning over the same Basics line; never write real contact details, salary or the like into a tracked file (tests use made-up ones). Generated CVs, cover letters and application answers may reorder, emphasize, rephrase and remove, and must NEVER add a skill, technology, employer, title, date, responsibility, achievement or metric that is not in that file. `TODO` entries are unknown: leave them out. Code reads the file in `profile.py` (`load_profile`, `sections`, `split_tags`, `strip_notes`); the checks on generated lines (numbers, names, skills, seniority words, years) share their building blocks in `grounding.py`, used by `check_draft` (pitch) and `check_bullet` (cv), so a change there changes both.
- Deterministic code decides filtering, dedup and eligibility, and every verdict carries a quotable reason. LLM judgment on eligibility belongs only on jobs whose eligibility is `unclear`. There is no review list (the user's call 2026-10-27): a job is rejected, shortlisted or visa_list, and an `unclear` or undated one is shortlisted, then the daily run's AI check and date lookup reject the ones they find quoted evidence against. The 183 jobs left in `needs_review` were cleared on the user's call (2026-10-29) by migration 2: rejected, code `review_cleared` (`models.REVIEW_CLEARED`), which `reclassify` skips, so they never come back (judged again, every one came out shortlisted). Do not replace a rule that quotes evidence with a guess. (Contacts and email drafts are separate LLM uses, each checked by code; see below.)
- Fit score (`fitgrade.py`, `rubric.py`, `interviews.py`, `config/fit_grade.json`, `jobhunter grade`; the user's rubric, 2026-11-15, decision 26, replacing the 1-5 grade learned from Applied/skipped examples): 0-100 for each shown job, for SORTING ONLY (report, To apply, which jobs get a CV first). It never changes `status`, never hides or rejects a job, and is stored in `jobs.fit_grade_json` (`score`, `parts` {name: [points, why]}, `culture` {tag, why}, the model's `answer`) so `reclassify` keeps it; an old 1-5 grade has no `score` and reads as unscored. Parts: seniority 15, skills 12, years 8, domain 5, visa/location 30, salary 7, benefits 1, equity 2, AI culture 20. Code adds them up, never the model. Claude Code (`claude-code:opus`) answers only seniority, required skills, domain, and the benefits/equity/AI-culture quotes; a quote `find_quote` cannot find in the posting scores nothing. Years (`required_yoe` vs the profile's years), visa/location (`rubric.visa_points`: the posting's own visa sentences via `visa.read_posting`, the sponsor registers named in the eligibility reasons, the AI check, the company's other stored postings offering a visa in 2+ different months: `fitgrade.other_offer`) and salary (`FIT_SALARY_FLOORS` in `.env`, per visa-list country code, else `default`; UAE/Qatar use `RELOCATION_MIN_MONTHLY_USD`; no pay = 0) are code alone; never write a floor into a tracked file. AI engineering culture (the user's call 2026-11-18, replacing the live-coding interview star; `rubric.Culture`, `culture_points`): AI-Native (AI-assisted coding, product ownership, rapid shipping) 20, Traditional (deep language expertise, unassisted coding, algorithm-heavy interviews) 0, Unknown 10, each with a one-sentence why, shown as a chip next to the score on every role in the app and as an "AI culture" line in the report. From the posting's own words, else `interviews.py` looks the company up once (table `interview_styles`, kept `interview_recheck_days`; rows checked before `CULTURE_FROM` asked about live coding only and are looked up again) with Claude Code web search (engineering blog, careers and how-we-hire pages, AI tooling), counted only when code finds the quote on the page it fetched itself (never Glassdoor, Reddit, Blind, levels.fyi, Kununu: `NO_FETCH`; the hiring-without-whiteboards list is no longer read: it says nothing about AI), then `rescore` (no model; also `jobhunter grade --rescore` after a floor changes) updates its jobs. A tag with no quote code found is Unknown. An answer stored before 2026-11-18 (`interview`, `star`) reads live coding as Traditional, the rest as Unknown, until `--regrade`. The `fit_score` keyword count stays only as a hidden tie-break. Skip reasons (`applications.skip_reason`/`skip_note`, `tracking.SKIP_REASONS`) are still kept but no longer feed the score. The user set Reached out / Interviewing by hand for other reasons: never use stages as like/dislike signals. The one exception (the user's call 2026-11-15: every card they move to Reached out is an application they submitted): moving a new or saved job to Reached out by hand also marks it applied (`tracking.move_by_hand`, used by the stage route), like the button; a move back from a later stage keeps the date it had. Senior roles are rejected (the user's call 2026-11-20, decision 30, after ~300 applications and 1 interview; it replaces the 2026-10-19 choice that 5+ years only cost points): code `too_senior`, quoted, when the title says "senior"/"Sr." (`senior.title_words` in `config/filters.json`), the text asks for a senior person (`relevance.senior_ask`: "We're looking for a Senior ...", "As a Senior ...", "Position level: Senior", "senior-level expertise"; a sentence that also names junior/mid is open to both, and naming senior colleagues is never an ask), or it states 5+ years (`reject_if_required_yoe_at_least` 5). It applies to the shortlist and the visa list alike.

- Dedup (`identity.py`, `store.find_match`) matches a listing to a stored job by source id, ATS id, else company + title (`fingerprint`, no location), and a match is only `touch`ed, never judged again. So a listing that names a different place than the stored row, on a job rejected **for where it is** (`_PLACE_CODES` in `pipeline.py`: not_remote, local_only, location_restricted, location_conflict, residency_required, timezone_restricted, no_sponsor, no_visa_evidence, below_relocation_pay), is classified on its own words (`pipeline._rejudge`): if it is not rejected, the row follows that listing (`store.adopt_listing` overwrites everything classify reads plus the links, drops the old ai/date check, keeps company, title and the identity keys) and the report lists it under "Listed somewhere else". The other codes are never revisited: two listings of one posting differ in their location text too, and a trimmed one would undo `too_old` or `too_senior`, whose evidence is in the text. A listing with no description never brings a job back (Getro has none), and a shortlisted job is never pushed down. The user's call 2026-11-11, decision 23 (Virtusa's London row had swallowed six Doha and Dubai listings).
- Duplicate roles (`duplicates.py`, code `duplicate_role`, the user's call 2026-11-14, decision 25): dedup keeps two postings with different ATS ids apart on purpose, so one company re-posting an opening (or two boards linking it differently) made the same role two and three rows, each with its own CV and its own card. After the rules judge a job, the copies of its role (same `fingerprint`, same place) are gathered and all but one rejected, the reason naming the job kept. The one kept is the copy carrying the user's work (applied, reached out, LinkedIn note, or skipped: `acted_on`; a tailored CV does not count, the daily run writes those), else the newest posting (a dated copy ahead of an undated one: the date lookup runs after `ingest` and may still reject the undated one). Only copies still `shortlisted`/`visa_list` are candidates (`store.lists.role_copies`), so a twin rejected `too_old` or for its country never swallows a posting the rules kept, and a copy the user acted on is never the one rejected (it is in no waiting list, and rejecting it would file a job they applied to under Rejected): 16 folds on the stored jobs, not 24. `same_place` is a word-subset test ("London" = "London, UK" = "London (hybrid), United Kingdom"; two bare-remote texts match; "Remote - India" and "Remote" do not), so the same title in another country stays its own job (Resonance, London and Berlin). Both `pipeline.ingest` (the new job's role) and `jobhunter reclassify` (every role, after the main loop) go through `duplicates.fold`, so they can never disagree and a second run changes nothing; nothing is read back as a fact, so changing the rule and re-running `reclassify` undoes it.

- The SQLite DB (`data/jobs.sqlite`) is the memory; Markdown reports are output only. Rejected jobs stay stored on purpose, so they never reappear as new. The schema is `SCHEMA` in `store/schema.py`, every column in its CREATE TABLE; a new column also needs a numbered migration there (`MIGRATIONS`, recorded in `PRAGMA user_version`) that adds it only when missing, since a new database runs every migration after SCHEMA. All SQL lives in `src/jobhunter/store/` (a module per group of tables, listed in its `__init__.py`); other modules call its functions and never touch `store.conn`, and status and stage names come from `models.py` as query parameters. Store functions never commit: the caller commits, before any network or model call, so no write lock is held while it waits.
