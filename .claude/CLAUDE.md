# Notes for agents working on this project

- `profile/master_profile.md` is the only source of facts about the user. It and `resume/resume.md` are not in git (`.gitignore`); git has made-up `*.example.md` copies. The user's name and contact details are `MY_*` in `.env` (`config.my_details`, and `my_details` in `build.py`), each winning over the same Basics line; never write real contact details, salary or the like into a tracked file (tests use made-up ones). Generated CVs, cover letters and application answers may reorder, emphasize, rephrase and remove, and must NEVER add a skill, technology, employer, title, date, responsibility, achievement or metric that is not in that file. `TODO` entries are unknown: leave them out. Code reads the file in `profile.py` (`load_profile`, `sections`, `split_tags`, `strip_notes`); the checks on generated lines (numbers, names, skills, seniority words, years) share their building blocks in `grounding.py`, used by `check_draft` (pitch), `check_bullet` (cv) and `check_sentence` (cover), so a change there changes all three.
- Deterministic code decides filtering, dedup and eligibility, and every verdict carries a quotable reason. LLM judgment on eligibility belongs only on jobs whose eligibility is `unclear`. There is no review list (the user's call 2026-10-27): a job is rejected, shortlisted or visa_list, and an `unclear` or undated one is shortlisted, then the daily run's AI check and date lookup reject the ones they find quoted evidence against. The 183 jobs left in `needs_review` were cleared on the user's call (2026-10-29) by migration 2: rejected, code `review_cleared` (`models.REVIEW_CLEARED`), which `reclassify` skips, so they never come back (judged again, every one came out shortlisted). Do not replace a rule that quotes evidence with a guess. (Contacts and email drafts are separate LLM uses, each checked by code; see below.)
- Fit grade (`fitgrade.py`, `config/fit_grade.json`, `jobhunter grade`): DeepSeek grades each shown job 1-5 with one sentence, for SORTING ONLY (report, To apply, which jobs get a CV first). It never changes `status`, never hides or rejects a job, and is stored in `jobs.fit_grade_json` so `reclassify` keeps it. It learns only from examples, never from rules you write for it: the profile's facts (via `profile.load_profile`, so no contact details), the user's `preferences` text, and their Applied jobs and skipped jobs with `applications.skip_reason`/`skip_note` (one-tap reasons, `tracking.SKIP_REASONS`). The user set Reached out / Interviewing by hand for other reasons: never use stages as like/dislike signals. Stated 5+ years is ranked down by the grade, not rejected (user's choice, 2026-10-19), except for the junior-only roles below.
- Years of experience (`extract.find_required_yoe`): read per sentence (a "nice to have" cancels only its own sentence), and the reason quotes the sentence. Check a new pattern against the stored jobs (old vs new `required_yoe`) before shipping: company history ("for the past 12+ years") and benefits ("after 5+ years") are not requirements.
- Junior-only roles (`junior_only` in `config/filters.json`, `relevance.junior_only_role`): AI engineer, AI automation and forward-deployed titles (a word from `roles`, or `_AI_ROLE`) are wanted only at junior level (the user's call 2026-10-20): rejected, code `junior_only`, when the title says "senior"/"lead" or the posting asks for 3+ years, quoted. A title that also says backend or full stack keeps the usual rules, as do backend, software and solutions roles (6+ rejected). The years can be in any field ("3+ years of software, 1+ with LLMs" counts as 3); no years stated is kept. FDE itself is kept for every country (the user's call, 2026-11-06: the stored jobs showed ~24 of 28 visa-list FDE jobs in London or Dublin, the German and Dutch ones already rejected as `language_required`, and UK/Gulf FDE roles the user reached out on), but "forward deployed" is in `title_include_needs_role`: it counts only when the title also names an engineering role (`_ENGINEERING_ROLE` in `relevance.py`), so "Forward-Deployed Banker" and "Forward Deployed AI Scientist" are `title_not_target`.
- Outreach (`jobhunter serve`, `src/jobhunter/web/`): `contacts.py` (Hunter first, Claude web search as backup; who to target by size is plain code; a web-found name is "confirmed" only when `find_quote` finds it in text the API returned), `pitch.py` (fixed text by default; with `pitch_mode` "ai" the model writes only the one-sentence proof line, through `llm.json_model`; `check_draft`, built on `grounding.py`, blocks any number, skill or title not in the profile facts it cites), `mailer.py` (Gmail app password: SMTP send, IMAP read-only scan), `tracking.py` (stages, follow-ups, ghosting). Emails are sent ONLY from the Send button (`POST /api/jobs/{id}/send`); never add automatic sending, including follow-ups. The tables `companies`, `contacts`, `applications`, `events`, `sent_mail`, `mail_seen` are separate from `jobs`, so `reclassify` never touches them. Pipeline order (the user's call 2026-10-23): To apply by posting day, newest first; Reached out by `reached_out_at` (later of applied/emailed, else when you moved it), newest first. Columns (the user's call 2026-10-29, Rejected added back on their call 2026-11-11): To apply (new or saved), Reached out, Replied, Interviewing, Offer, Rejected (closed with reason `rejected`), Closed (the other reasons: skipped, ghosted); no Saved or Email someone column, since every applied job gets a LinkedIn note (the apply-job skill writes it, the user sends it). Rejected and Closed are the same stage `closed`, split in `BOARD`/`boardKey` in `app.js` by `closed_reason`: display only, no new stage and no migration, and moving a card there closes it with reason `rejected` (`reason` on the column) instead of asking why. The column asks for its own list, the `closed_rejected` view in `JOB_VIEWS` (`store/lists.py`), because `job_list` stops at 500 rows and the hundreds of skipped jobs in Closed would hide the oldest rejections; the board drops the rejected rows from the closed list so no card shows twice, and falls back to that filter when the call 400s (an app still running the older code). A job's card carries the LinkedIn note (the user's call 2026-11-05): `applications.linkedin_url` and `linkedin_note` (migration 3), one **LinkedIn** box on the card with the link to the person, the note and its count (300), both saved on blur through `PATCH /api/jobs/{id}/application` (`clean_linkedin` in `contacts.py` refuses a link that is not linkedin.com), filled by the apply-job skill with `jobhunter linkedin <id> --url ... --note ... --followup ...`; the card has no Who to contact box, no subject, and no Fill template, Save, Copy or Send button, and nothing is ever sent (the user presses Connect). The contact lookup, drafts and sending stay in the code and in the API for the inbox check and old jobs, which keep their drafts: nothing was copied over. A job also carries the follow-up and where it is on LinkedIn (the user's call 2026-11-07, after the week-one review in `reports/linkedin_review_2026-11-07.md`: the invite worked, 25% accepted on the batch old enough to judge, but 8 of the 10 who accepted were never written to again): `applications.linkedin_followup` and `linkedin_sent_at`/`linkedin_accepted_at`/`linkedin_replied_at` (migration 4), the step dates ticked by hand on the card (`linkedin_sent`/`_accepted`/`_replied` in `PATCH /api/jobs/{id}/application`, each writing an `events` row; `set_linkedin_step` names the column from `LINKEDIN_STEPS`, never from the request) and backfilled with `jobhunter linkedin <id> --sent-at ...`. Accepted with no reply gets an "accepted · follow up" chip and the `linkedin_waiting` view; the invite-note rules themselves did not change (the user's call 2026-11-07), and the follow-up is not checked against the profile: apply-job grounds it when it writes it. Nothing is ever sent, the follow-up included. The Jobs tab's Shortlisted and Visa list views show only jobs not acted on yet (stage new or saved, `_WAITING` in `store/lists.py`); one you reached out on is under Tracked (the user's call 2026-11-01: old reached-out jobs read as new shortlisted ones).
- Rejection emails (`rejections.py`, the user's call 2026-10-31): the inbox check (`mailer.check_inbox`, so both daily runs, `jobhunter inbox` and the app's Check inbox) searches Gmail since the oldest open application and closes a job as `rejected` when an email has a sentence matching `REJECTION` (never one with "if"/"should"), is about an application, came after the application started, and names the company in its sender or subject (never the body: short names like Wise, IMC; job boards in `_NOT_EMPLOYERS` skipped). The job is the one whose title the email names, else the company's only open application; with several open and none named nothing changes and the email is listed in the result's notes. The event quotes the sentence and how the job was picked. `auto_close_rejections` / `rejection_lookback_days` in outreach.json; `jobhunter inbox --dry-run` lists what would close. Emails read as rejections go in `mail_seen` (`rejection`, or `rejection_other` when no open job was picked), so a second run changes nothing; any other email is read again each run, so a phrase added later still catches it. No model: add a phrase only after checking it against real emails.
- Web app security: 127.0.0.1 only, Host check, and every change request needs the startup token (`X-JH-Token`) and a JSON body. Keep it that way; no CORS, except GET `/api/cv/...` (`Access-Control-Allow-Origin: *` and `Allow-Private-Network`), so the Chrome extension can attach a CV on a job site; it only reads PDFs listed in `cv_dir`. Each write route takes a Pydantic request model (a wrong value is a 400 naming the field); every error is `{"error": ...}` with the status of its `errors.py` kind (400, 404, 409, 502). A GET never writes: `contacts.job_company` reads (a missing companies row reads as `new_company`'s defaults), `ensure_company` creates it for the actions that need it. The job list loads its contacts in bulk (`chosen_contacts`): no query per row.
- Tailored CVs (`cv.py`, `jobhunter tailor`, the Tailor CV button): the model only orders and rewords profile bullets and picks skills; code copies names, employers, dates and education from `resume.md` in `resume_dir` and checks each bullet against the profile bullets it cites (`check_bullet`), each skill against the profile row. A rewrite never shortens a bullet: it may drop at most `MAX_DROPPED_WORDS` (1) of the cited bullet's words, and code puts back the profile's bold (`restore_bold`: `**800+**`), which the model's text does not carry (the user's call 2026-10-23: the model had cut clauses and an "estimated"). The headline is the posting's own title, cleaned by code (`cv_headline`: "Senior Software Engineer, Payments Platform" -> "Senior Software Engineer", "Senior Backend & Platform Engineer" -> "Senior Backend Engineer", levels like II and words like Remote/Junior/Freelance dropped; the user's call 2026-10-23; "Developer" prints as "Engineer" and "Back End" as "Backend", the user's call 2026-11-04, like the role titles' `Printed title:` lines); a title that does not read as one engineering role gets the model's pick from the target roles, with a note. A failed rewrite prints the profile's own words. The model never writes a Summary: the `## Summary` paragraph in resume.md is the user's own (also in the profile, stated 2026-10-20) and is copied word for word like the other non-role lines. `build.py` in `resume_dir` makes the PDF; never overwrite a version the app did not write. Your hand edits (`cv.save_version`, the Edit CV text box, `jobhunter rebuild-cv`) are the exception: they rewrite the job's `versions/<name>.md` (keeping `.md.bak`) and only rebuild the PDF, with no model; `check_version` lists lines that say more than the profile but never changes them. A tailored CV with `edited_at` is not re-tailored unless `replace_edits`.
- The profile is the bullet library: every Experience bullet starts with tags (`[core]` always prints; `[lead]`/`[fullstack]`/`[automation]`/`[mobile]` only when `cv.job_tags` matches the job, by phrases in `TAG_RULES` or `cv_tags` in outreach.json, each with a quotable reason). Which bullets print is code's decision, never the model's; a bullet the model leaves out is appended in the profile's words. `Printed title:` lines choose the role's title the same way; the `###` heading keeps the real title, which `_match` also accepts. Notes on a bullet must be `(Confirmed by me ...)` or they print; any other `- ` line under a role becomes a bullet. Tests use a frozen copy, `tests/fixtures/profile/master_profile.md`, because they cite bullets by position; `test_your_profile_is_well_formed` checks only the shape (known tags, no leaking notes) of the real profile, when there is one, and of the example, so editing the real profile never needs test changes. A CV still 2 pages in compact mode drops optional bullets (`cut_optional`, oldest role first), never core ones. `build.py sync` (in `resume_dir`) copies the tagged bullets into resume.md; `build.py new <Role> <Company> [tag ...]` applies the same tags by hand.
- Cover letters (`cover.py`, `jobhunter cover`, the Write cover letter button): only when the user asks; the daily run writes none (`auto_cover` false, the user's call 2026-10-20). Only two paragraphs, no header, date, greeting or sign-off (the user's call 2026-10-20); the page's Download button saves the text as `.txt` in the browser: (1) why this company, written by `cover_model` (`claude-code`, the user's pick over DeepSeek on 2026-10-20: DeepSeek read as AI) from the posting and up to 3 pages code fetches from the company's site (`research`: home, /about, /blog; domain from `companies.domain`, the job's links, else a `<name>.com` guess kept only when the page names the company; none for job boards/agencies), and (2) `cover_paragraph` from outreach.json, the user's own words, printed as is and never checked. `check_sentence` makes every name, number and company-kind word (`_COMPANY_KIND`: "consultancy", "startup") be in the posting, the pages or the profile facts (`load_letter_facts`, the CV's tags, never logistics lines); a sentence with I/my names only profile tools and years. Paragraph 1 is about the company, never a pitch: the writer never sees the profile facts (they are only for the checks), and a sentence that describes the user's past work (`_PAST_WORK`: "I built/led", "my experience", "similar") or names an employer is dropped; a number is sent back once (their headline stats read as a website summary). The model names its one reason, then quotes the words it rests on (`find_quote`); a third try only when too little would be left. A sentence that fails after one retry is dropped and listed in `removed`; length (2-3 sentences, 65 words), dashes and an unfound quote are sent back once, then noted. How paragraph 1 reads lives in `config/cover_letter_guidelines.md` (the `writer:start`/`writer:end` part follows `SYSTEM`; `check_style` reads its "Never use" and "Use at most one" lists); the facts rules stay in code. Stored in `applications.cover_letter_json`; the file is `cv_dir/<Last>_CoverLetter_<Company>_<MonYYYY>.md`; never overwrite a letter the app did not write.

It changes a status only when its quote is found word for word in the description or a page the API or code fetched (`find_quote`); never trust a quote only the model saw; `classify.apply_ai_check` combines it with the rules, and results live in `jobs.ai_check_json` so `reclassify` keeps them. Its verdict `sponsors_visa` (the company sponsors a work visa for the role, in any country: the user's call 2026-10-22) shortlists the job as `likely` (`ai_sponsors_visa`) only when the quote is found and `visa.read_posting` also reads it as an offer with no refusal. The 401(k) rule still applies to these.
- Location conflicts (`eligibility._assess_remote`): a location that fits, narrowed somewhere else ("Worldwide", but "must be based in the UK"; "EMEA", but location "Remote, United Kingdom"), is rejected, code `location_conflict`, quoting both (the user's call 2026-10-22); narrowed to the UAE/Qatar the relocation rules judge it, to a visa-list country the visa rules, to Kuwait or Bahrain the `gulf_remote` rules (remote only; see the bullet above). A restriction the posting doubts ("Remote - Europe (UTC-1 to UTC+3)", "US only" next to "we hire globally") stays `unclear`. A salary-range sentence ("applies to US-based candidates only") is not a location rule.
- Posting dates (`posted_date.py`, `jobhunter dates`, `find_dates` in `config/ai_check.json`): an undated job is shortlisted with a note, and before the AI check the daily run looks up undated shortlisted jobs: code reads the schema.org `datePosted` on the job's own pages, else `web_model` (Claude Code with web search) quotes the words that state the date; code finds the quote on the page it fetched and reads the date from the quote (`date_in`), never the model's own date. The date goes into `posted_at`, the evidence into `jobs.date_check_json`, and the usual age rule judges the job.
- A source's "no location given" is unknown, never "Worldwide" (Himalayas shows "Worldwide" for US-only roles).
- Himalayas re-lists old jobs with a new `pubDate` and keeps `expiryDate` (2026-11-01: about 70% of its jobs, Hivex's from mid-October among them). A first listing runs a whole number of days (almost always 60), so `himalayas.listed_at` marks a job whose span is not whole with a `DateCheck` (`found_by` "himalayas") quoting both dates, and classify rejects it as `too_old` (the user's call 2026-11-02: 73 of 83 re-listings checked were over 14 days old; no feed gives the first date, and expiryDate - 60 days, its `posted_at`, is only the latest it could be: Elm AI's said Oct 25, its page July 30).
- freehire (`sources/freehire.py`, the user's go-ahead 2026-11-13, research in `docs/research/2026-11-13-freehire-as-a-source.md`): one aggregator over ~450 sources we do not read (Workday, Oracle, iCIMS, JazzHR, Bayt...), public API, no key. Its `posted_at` is re-dated (a median 18 days late against the same posting from its own board), so a job is dated by the earlier of `created_at` and `posted_at`. Its country codes are never used (it tagged "Toronto, Canada" as the UK): the location is the posting's own text, else unknown. `skip_sources` leaves out `whatjobs-*` (re-posts under rewritten company names, which hid an agency from `agency.py` and brought back a rejected job) and boards that post in Russian or Spanish; a company name with a glued legal form ("eworgmbh") gets its space back so `agency.py` still matches it.
- Dedup (`identity.py`, `store.find_match`) matches a listing to a stored job by source id, ATS id, else company + title (`fingerprint`, no location), and a match is only `touch`ed, never judged again. So a listing that names a different place than the stored row, on a job rejected **for where it is** (`_PLACE_CODES` in `pipeline.py`: not_remote, local_only, location_restricted, location_conflict, residency_required, timezone_restricted, no_sponsor, no_visa_evidence, below_relocation_pay), is classified on its own words (`pipeline._rejudge`): if it is not rejected, the row follows that listing (`store.adopt_listing` overwrites everything classify reads plus the links, drops the old ai/date check, keeps company, title and the identity keys) and the report lists it under "Listed somewhere else". The other codes are never revisited: two listings of one posting differ in their location text too, and a trimmed one would undo `too_old` or `too_senior`, whose evidence is in the text. A listing with no description never brings a job back (Getro has none), and a shortlisted job is never pushed down. The user's call 2026-11-11, decision 23 (Virtusa's London row had swallowed six Doha and Dubai listings).
- Duplicate roles (`duplicates.py`, code `duplicate_role`, the user's call 2026-11-14, decision 25): dedup keeps two postings with different ATS ids apart on purpose, so one company re-posting an opening (or two boards linking it differently) made the same role two and three rows, each with its own CV and its own card. After the rules judge a job, the copies of its role (same `fingerprint`, same place) are gathered and all but one rejected, the reason naming the job kept. The one kept is the copy carrying the user's work (applied, reached out, LinkedIn note, or skipped: `acted_on`; a tailored CV does not count, the daily run writes those), else the newest posting (a dated copy ahead of an undated one: the date lookup runs after `ingest` and may still reject the undated one). Only copies still `shortlisted`/`visa_list` are candidates (`store.lists.role_copies`), so a twin rejected `too_old` or for its country never swallows a posting the rules kept, and a copy the user acted on is never the one rejected (it is in no waiting list, and rejecting it would file a job they applied to under Rejected): 16 folds on the stored jobs, not 24. `same_place` is a word-subset test ("London" = "London, UK" = "London (hybrid), United Kingdom"; two bare-remote texts match; "Remote - India" and "Remote" do not), so the same title in another country stays its own job (Resonance, London and Berlin). Both `pipeline.ingest` (the new job's role) and `jobhunter reclassify` (every role, after the main loop) go through `duplicates.fold`, so they can never disagree and a second run changes nothing; nothing is read back as a fact, so changing the rule and re-running `reclassify` undoes it.
- One company, one box (`byCompany`/`companyBox` in `app.js`, the user's call 2026-11-14): the Jobs tab's two waiting views (`GROUPED_VIEWS`: shortlisted, visa_list) and the Pipeline's To apply column draw a company's jobs in one box, its best job (grade, then fit) on top and a button counting the rest, which opens them in place (`state.expanded`, the `data-more` handler). Today's triage lists keep the old flat `onePerCompany` + `moreButton`, and Tracked, Closed, Rejected and `linkedin_waiting` stay flat (jobs already being worked: a second one at the same company must not sit behind a button). Display only, like `report.one_per_company`: never a status, a reject code or the CV step.
- The SQLite DB (`data/jobs.sqlite`) is the memory; Markdown reports are output only. Rejected jobs stay stored on purpose, so they never reappear as new. The schema is `SCHEMA` in `store/schema.py`, every column in its CREATE TABLE; a new column also needs a numbered migration there (`MIGRATIONS`, recorded in `PRAGMA user_version`) that adds it only when missing, since a new database runs every migration after SCHEMA. All SQL lives in `src/jobhunter/store/` (a module per group of tables, listed in its `__init__.py`); other modules call its functions and never touch `store.conn`, and status and stage names come from `models.py` as query parameters. Store functions never commit: the caller commits, before any network or model call, so no write lock is held while it waits.
- Reports are `reports/<YYYY-MM-DD>.md`, one per day, rendered from `jobs.report_date` (see `store/jobs.py`); there is no `latest.md` or run-numbered file. A date-range run (`--from/--to`) fetches once and files jobs by posting day.
- Watched boards (`boards.py`): after each run, the Greenhouse/Lever/Ashby board of each company with a shortlisted job is added to the `watched_boards` table (from the job's own link, or a guessed slug kept only when the board lists the job's title or names the company, with that evidence as `reason`) and fetched from the next run on. Never job sites, agencies or blocked companies; a removed board stays removed. Settings: `watch_boards` in `config/sources.json` (not a source; `sources.SETTINGS`).
- Agencies (`agency.py`, `agencies` in `config/filters.json`): rejected right after `blocked_companies`, code `agency`, quoting the name, the name word or the sentence. Only add a phrase after checking it against the stored jobs: "our clients", "talent pool", "talent network" are in real companies' postings.
- Relocation (`relocation.py`, `relocation` in `config/filters.json`): in the UAE or Qatar an on-site/hybrid job (or "Remote (UAE)") is judged by `assess_relocation`, never `unclear` (so the AI check, which asks about remote hiring from Lebanon, skips it). The pay floor is `RELOCATION_MIN_MONTHLY_USD` in `.env`, never in a tracked file. AED/QAR/SAR pay with no period is monthly (`extract._MONTHLY_BY_DEFAULT`).
- Kuwait and Bahrain (`gulf.py`, `gulf_remote` in `config/filters.json`, the user's call 2026-11-13, decision 24): companies the user would work for from Lebanon but would NOT move to, so the relocation rules' opposite. Only a **remote** job listed there counts, and it is never shortlisted on evidence of its own: it is `unclear`, code `gulf_remote`, quoting the location, so the daily AI check decides whether they can hire someone in Lebanon (it is told this reason: `ai_check.rule_reason(job, filters)`, passed by `check_jobs`, instead of re-deriving a reason without the filters, which read "Restricted to ..." and answered the question for the model). On-site or hybrid there is rejected `not_remote` like anywhere else; a posting that wants someone already in the country is `local_only` (the shared `relocation.local_only`/`title_local_only` lists, whose general wording is what matches here; "must be based in Kuwait" is caught by the description rules instead); an AI check that says cannot_hire while only quoting the location back is not used (`classify.gulf_quote_adds_evidence`: the rules kept the job knowing where it is listed, and the model is told a country list means cannot_hire; a quote that says the job is not remote, names anywhere else, or wants someone already there does count), and `sponsors_visa` is only a note here (a visa means moving); adding this list may keep more jobs than before, never reject more, so a posting that doubts its own location (`desc.specific_positive`, or a time zone window in the field) is still left for the AI check with the narrowing sentence quoted, a nationals-only title being the one exception; a location that names another place too ("Bahrain; India") is `location_restricted` as before (`only_place` removes the Kuwait/Bahrain words and classifies what is left). Nothing in the 37k stored jobs moved: the value is in the new searches (freehire `work_mode: remote` over kw/bh, LinkedIn with "remote" in the keywords since its logged-out remote filter does nothing, the Gulf Getro boards' `searchable_locations`; SerpApi left alone, its credits are nearly spent; no company careers boards there yet). Do not add a country here without the user's call.
- Visa list (`visa.py`, `sponsors.py`, `visa_list` in `config/filters.json`): a target role in the Netherlands, Germany, Finland, the UK, Ireland, Spain or Italy (on-site/hybrid, or remote only for people living there, i.e. one the remote rules reject) gets status `visa_list`, a separate list (report section, web view `visa_list`), never `shortlisted`, so it stays out of the report's Shortlisted section and the daily CV/letter/contact steps. The pipeline's To apply column does show the ones posted today or yesterday (stage new, the date the row shows: `view=visa_list&days=2`, with a `visa` chip), next to the shortlisted jobs. Only with quoted evidence: the posting offers a visa (`visa_offered`, also an HN "VISA" header), offers relocation help without naming a visa (`relocation_offered`, weaker), or the company is on its country's government list (`visa_register`: UK Skilled Worker register, Dutch IND recognised sponsors, Irish employment-permit companies; on-site/hybrid only). Rejected: `no_sponsor` (refuses, or wants a right to work, including a British nationality: "Sole British National", "must be a UK national"; never "UK national security clearance"), `language_required` (asks for or is written in a language not in the profile), `no_visa_evidence`. Each clause is judged alone ("Visa sponsorship available (no relocation support)" is an offer), except a refusal the clause split would cut ("Visa Sponsorship: Not available"; "unable to offer fully remote work, visa sponsorship, or relocation support"); "sponsorship" alone never counts, and a visa transfer only ("For local candidates we are able to support transfer of visa sponsorship") is a right to work you must already have. A remote job open to Lebanon is never moved to the visa list. The lists live in `data/sponsors/` (`jobhunter sponsors --update`; the daily run refreshes them every `refresh_days`); a one-word UK name needs the register's town in the job's location. The Gulf `relocation` rules are separate and unchanged.
- A posting that mentions a 401(k) is rejected (`classify.us_benefits`, code `us_benefits`, the line quoted), whatever its location or AI check says, unless it is on the visa list (it sponsors the move; big companies list every country's benefits): the user's call (2026-10-19), knowing it also drops global-remote companies like Metabase that offer one to US staff. Do not soften it into a doubt or a grade signal.
- One job per company (`report.one_per_company`, `onePerCompany` in `app.js`): the report sections, the To apply column and Today's new-job lists show each company's best job (grade, then fit) and name or fold the rest ("Also at Palantir (16 more)", "+16 more at Palantir"): one board fetch brought 17 Palantir London roles on 2026-10-21 (the user's call). Display only: never a status, a reject code or the CV step.
- `blocked_companies` in `config/filters.json` rejects a company before any other rule (code `blocked_company`, its `why` quoted): companies the user never wants shortlisted again.
- After changing `config/filters.json` or the rules, run `.venv/bin/jobhunter reclassify`.
- Tests: `.venv/bin/pytest`. A new source = a module in `src/jobhunter/sources/` with `from_config()`, an entry in `BUILDERS`, and a test against a trimmed real response in `tests/fixtures/`. A careers board per company (Greenhouse, Lever, ...) subclasses `BoardSource` (`sources/base.py`) and writes only `postings()` (one board's raw postings) and `parse()` (one posting as a Job): a broken board or posting then costs only itself, through `parse_each`. CI (`.github/workflows/ci.yml`) runs `ruff check .` and `pytest` on Python 3.11 and 3.12; keep both clean. `tests/fixtures/hunter_*.json` are Hunter's documented examples (no key yet): replace them with trimmed real responses once `HUNTER_API_KEY` is set. Tests never reach Hunter, Claude or Gmail (`conftest.no_real_keys`).
- LinkedIn (`sources/linkedin.py`) is read through its logged-out job search, the user's choice (2026-10-21) knowing its terms forbid it: keep it slow (`pause`, about 1 request/s gets 429), by place (UAE, Qatar, Lebanon, UK/NL "visa sponsorship"; logged out the remote and level filters do nothing), and never fetched twice in a run (`refetch = False`, like SerpApi). Remote Rocketship's terms forbid scraping: do not build it.
- Each run waits for the network first (`http.wait_for_network`: the scheduled runs start as the Mac wakes) and fetches a source with a ConnectError once more (`pipeline.fetch_all`).
- Error lines go through `sources.base.describe_error`, which drops query strings, so the SerpApi key never reaches logs or reports. The `httpx` logger stays at WARNING for the same reason.
